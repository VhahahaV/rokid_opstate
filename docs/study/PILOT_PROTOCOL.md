# OPSTATE 小规模试用与版本冻结

状态：执行方案，尚无真实参与者结果。目标为 V5 要求的 4–6 人 pilot；模拟数据和设备测试不计为参与者。

## 启动条件

正式试用前必须有对应构建的验收证据：30 分钟连接稳定、至少 50 次拍照往返且成功率不低于 95%、20 次模型请求协议检查、20 次真实服务可见 ACK、重复抑制与材料变化重新服务、未来信息隔离、导出校验。小型生成输入的模型接口检查不能替代长历史模型效果。

需准备手机、眼镜、电脑/包/出口等场景道具，以及已校验的公共场景或 R6 历史。Rokid 授权和模型 Key 保存在应用私有凭证区。模型与场景冻结后再开始记录。

## 每位参与者的流程

1. 使用代号 P001 等，与姓名联系信息分开保存。说明眼镜会按计划拍照、可暂停与结束，不保存原始音频和 IMU。
2. 演示连接、历史进度选择、开始实时服务、暂停、手动拍照和眼镜收起卡片；练习记录与正式记录使用不同会话。
3. 选择预先确定的历史锚点或会议场景，记录条件和版本。正式沉默评估关闭眼镜演示视图；需要评估演示体验时单独运行并标记。
4. 参与者按日常步骤处理桌面工作、收拾物品和准备出发。操作员只注入事先写好的公共情境，不代填模型答案，也不根据模型输出临时更改预期标签。
5. 包含一次公共材料变化，并保留服务后再次检查的窗口，观察重复抑制和重新服务。发生质量失败、超时或无可见 ACK 时按技术失败记录，不补写成功回执。
6. 结束后导出完整 ZIP，运行校验和指标工具，填写下方问卷，记录不适、看不清、状态不明确或操作中断的位置。

主要条件使用 `BENCHMARK_ALIGNED`。如比较 `DEPLOYMENT_OPTIMIZED`，采用独立会话并交错顺序：4 人可分为 2 个 A→B、2 个 B→A；6 人各 3 个。不要把两个条件混成一条连续历史。`shadow_inference` 属于仅记录结果的独立条件，没有真实服务回执。

## 试用后问卷

以下为本项目自编的探索性问卷，不作为已验证的标准量表。每项选择 1–5 或“不适用”：1=非常不同意，5=非常同意。没有实际看到服务时，服务相关题可以不适用。

| 项目 | 评分 |
|---|---|
| 提醒出现的时机合适 | 待填写 |
| 提醒内容对当前任务有帮助 | 待填写 |
| 眼镜上的内容容易看清和理解 | 待填写 |
| 我能理解当前处于历史准备、运行还是暂停状态 | 待填写 |
| 手机上的进度、拍照和合成情境操作方便 | 待填写 |
| 提醒打断了我原本的活动 | 待填写；此题高分表示打扰更强 |

开放问题：哪些时刻希望有提醒却没有？哪些提醒没有帮助？哪里不清楚或需要反复操作？最想改善的一项是什么？

问卷单独保存并关联 `participant_alias/session_id`；它是评估数据，不加入模型因果上下文。

## 分析计划

- 先检验数据完整性，再分析行为结果。按实际相机/模型/显示来源分别报告测试替身与真机样本。
- 分别报告拍照往返完成率、图像质量通过率、模型技术失败、服务投递失败和真实回执，不合并成一个“成功率”。
- 报告各阶段样本数、median/P95、最长延迟及中断；不足 20 个样本的分位数不作为对应性能 gate 通过的证据。
- 沉默评估使用眼镜屏幕前后对照和发送命令记录；零回执本身不能证明没有任何 UI 变化。
- 保留 waiting、already-served、无新增价值等负例；评估侧的标签与说明不进入公共模型请求。
- pilot 主要用于发现交互问题和校准阈值，逐参与者呈现结果。阈值调整后产生新冻结版本，不回改旧会话或把不同版本的指标合并。

## 冻结与交付

每次试用保留完整会话 ZIP、`SHA256SUMS.txt`、手机/眼镜实际 APK 与哈希、固件版本、model ID、发送参数、prompt/parser/preprocess/schema 哈希、场景或公共数据哈希、调度和采样参数、问卷与本分析计划的版本。

新运行时把实际安装的手机 APK（含 split APK）记录进 `phone_build`，并通过握手获取眼镜版本与 APK 哈希。重连时发现眼镜构建改变会暂停，要求开始新会话。旧导出中未记录的构建信息不能推测补写。

```bash
.venv/bin/python tools/validate_runtime_trace.py /path/to/unpacked-session
.venv/bin/python tools/report_runtime_metrics.py /path/to/unpacked-session
```

上面第二条输出用于分析，不能代替现场连续稳定性与实际服务序列验收。
